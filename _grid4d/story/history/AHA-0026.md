# AHA-0026: llm key helper: the safe run and the bound consumer are two executables, and verification of a safe path goes through the bound run

> llm key helper: the safe run and the bound consumer are two executables, and verification of a safe path goes through the bound run

**Type:** default
**Epic:** [AHABASE](AHABASE)
**Status:** completed
**Blueprint:** implementation-story-blueprint

## Goal

Serves AHABASE-Priorities rows 1 (safe) and 2 (llm): the Human's provider keys should live in the safe, not as literals in a shell profile. The released llm package (AHA-0024) defines the `safe://NAME` path form and the key helper, but two measured gaps keep a `safe://` path from working for a caller whose provider table lives outside the package (the method):

1. `session.key_value` launches the safe's bound run and the bound inner helper with ONE executable: `[exe, "safe", "run", ...] -- [exe, "llm", "key", PATH, "--emit"]`. The method's helper executable is its own command (it holds the provider table; the ahabase door ships none) and that command has no `safe` group. The two roles are different programs.
2. `verify_path` resolves a `safe://` key in-process (`resolve_key` then `resolve_auth`), which the safe's bound-consumer check refuses for any command that is not itself the bound helper. A verification or switch preflight of a `safe://` path can therefore never pass.

The change is additive and keyword-only: a `safe_executable` (the program that runs `safe run`, default `ahabase` on PATH) next to the existing `executable` (the bound inner helper), and verify/switch obtain a `safe://` token through the bound run.

Ontology first: the access-path and settings-switch blueprints state that the value reaches only the bound helper process; the implementation blueprint gains the two-executable statement. Then implementation, then tests with red controls (a planted canary never reaches output, logs or files).

## Requirements

### R1: Ontology and blueprints state the two roles

The implementation blueprint's key-helper paragraph and the transport paragraph name two executables (the safe's runner and the bound helper), and the owner-step table binds the helper executable, not necessarily the door.

**Acceptance Criterion:** the blueprint paragraph names both roles and the owner step binds the helper executable; the ontology concept text is unchanged or amended in the same words.

### R2: `key_value` separates the runner from the bound helper

`key_value(path_id, ..., executable=None, safe_executable=None)`: the outer command is the safe's runner (`safe_executable`, default `ahabase` on PATH), the inner is the bound helper (`executable`). Keyword-only; omitting `safe_executable` keeps the released behaviour (one program for both roles), so no caller changes meaning. The command is always `<runner> safe run ... -- <helper> llm key ... --emit`, so a helper without a `safe` group fails the run and never runs outside the safe's gate (stream A's fail-closed question, answered by construction).

**Acceptance Criterion:** a test with a fake runner records the exact outer and inner command lines for both roles and for the default; a canary value reaches only the child's output, never the parent's stderr, the error message or any file; red controls: the roles swapped, the default dropped.

### R3: Verify and switch obtain a `safe://` token through the bound run

`verify_path` and `switch_path` (and `first_working_path`, `verify_path_family` which forward) accept `executable` and `safe_executable`; when the caller names its own helper (`executable`), a `safe://` token comes from `key_value`; without it the released in-process check with `argv` and `safe` stays, a refusal is status `auth-refused` with a message that holds no value.

**Acceptance Criterion:** tests with a fake runner show a `safe://` path verified with the canary token sent to the stubbed endpoint and absent from the verdict, and a refused run gives `auth-refused`; an `env:` path is unchanged; red control: the in-process resolution restored makes the safe path refuse.

### R4: Release

**Acceptance Criterion:** the full suite and the three-platform matrix are green on the story branch; the release tag is produced by the completion.
