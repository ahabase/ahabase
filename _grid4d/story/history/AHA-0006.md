# AHA-0006: safe threat model: assets, attackers and vectors - supply chain, prompt injection through agents, plugins, local processes, disclosure - with controls, residual risk and new design rules

> Is a publicly described credential mechanism a target? The design may be public; the key material and the target map may not - and the agent path must be closed first.

**Type:** default
**Epic:** [AHABASE](AHABASE)
**Status:** completed
**Blueprint:** [implementation-story-blueprint](implementation-story-blueprint)

## Goal

The Human asked (2026-10-25) whether describing publicly how the safe handles credentials makes it a target, also through AI agents. This story writes the safe's threat model: assets, attackers, threats in the STRIDE classes, and for each threat the controls in place, the controls designed and the risk that remains. It derives new design rules - consumer binding, reveal by a person only, agent defaults - records them in the ontology and orders the next steps so that prompt injection through agents is closed first. No code is written; nothing on the instance changes.

## Requirements

### R1: Threat model

Assets (safe values, the target map, the package, the model's context and transcripts, the screen), attackers (remote, plugin or dependency, local process, audience) and threats T1-T11 (T9 tampering with the manifest and the safe's location, T10 spoofing, T11 the equality oracle of `safe compare`, added in review) with repudiation, each with vector, today's controls, designed controls and residual risk; the reasoning why the design may be public (Kerckhoffs's principle) and what must stay private.

**Acceptance Criterion:** The threat-model blueprint exists with Assets, Attackers, Threats (T1-T11, each with the four parts; every STRIDE class carried by a labelled row) and Rules, and verifies; the consumer binding states its rules (absolute path, no shells, interpreters, wrappers or general-purpose network tools, minimal environment).

### R2: New design rules in the ontology

Consumer binding (allowed consumers per manifest entry), reveal by a person only, agent defaults and a network allow-list, declared safe access of plugins, and the manifest outside any git working tree - each marked designed in the concept it belongs to.

**Acceptance Criterion:** Manifest, Safe Value, Agent Guard and Plugin carry the designed rules with a link to the threat model.

### R3: Order of the next steps

The agent path (consumer binding, reveal by a person only, the agent guard) comes before `safe scan`; every document that states an order says so.

**Acceptance Criterion:** The threat model, the integration blueprint, the architecture blueprint and the idea's promotion path agree on the order; the idea's condition of an honest threat model links the model.

### R_team: Team-work quality

**Acceptance Criterion:** One review round on both instances with a 45-minute deadline, content frozen; every verdict recorded with its commit; friction logged.

### R_docs: Documentation

**Acceptance Criterion:** The threat model, the concepts, the blueprints and the idea agree.
