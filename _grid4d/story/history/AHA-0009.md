> Make ahabase's consistency visible by software: every concept traced to its implementation blueprint, every blueprint to its code, every module back to its blueprint - and a generated map of the ontology, never hand-written.

## Goal

The first step of the order the Human decided in [AHA-0008](AHA-0008) (decision 1: transparency before the agent guard). Today ahabase's consistency is checked by people and by per-story test rows, not by software across the Epic: the AHA-0008 lanes counted the gaps by hand, and the method's generators skip ahabase or read the wrong source. This story adds the declarations that make the lineage computable and a small core in the package that computes it - base territory by the boundary criterion (structure that software can verify).

Measured in AHA-0008 (transparency lane, prototype B on a clone): a stdlib-only core of about 120 lines gave 16 concepts, 33 typed edges, byte-identical regeneration, and 19 lineage rows with exactly the hand-counted gaps.

## Requirements

### R1: Lineage declarations

**Acceptance Criterion:** The Epic identity carries `**CodeArtifacts:** src/ahabase`. Every implementation blueprint carries a `**Code:**` line - module names relative to the package (`safe, cli_safe`), or `none (document blueprint)` for a blueprint that is a document by design (the Human's decision 4 of AHA-0008). Every module of `src/ahabase` carries an `Implements:` line in its docstring naming its implementation blueprint. A projections declaration (`ahabase-projections-pattern.md`) names the generated pages of the Epic.

### R2: The ontology map, generated

**Acceptance Criterion:** `ahabase ontology graph` writes a mermaid concept map into the ontology index between `<!-- ontology-map:begin -->` and `<!-- ontology-map:end -->`, from the index's vocabulary and every concept blueprint's Relations; running it again changes no byte; `--check` exits non-zero when the block is stale or edited by hand, and names the difference.

### R3: The lineage check

**Acceptance Criterion:** `ahabase verify` computes the Epic-scope lineage (concept -> implementation blueprint -> code module, and module -> blueprint through the docstring) and reports, by class: concepts without an implementation (separated by the concept's State - planned concepts are expected), document blueprints, blueprints whose `Code:` names a missing module, modules no blueprint names, and modules whose `Implements:` does not match. It exits non-zero on any divergence; on today's tree after R1 it reports exactly the expected gaps. A planted gap (a `Code:` line removed, a docstring back-link removed, a module added without a blueprint) turns it red.

### R4: Knowledge of the new capability

**Acceptance Criterion:** The concepts the core verifies are defined in the ontology with Placement and State (which ones - for example Lineage and Projection - is the design consult's question); an implementation blueprint describes the core with its `Implements:` and `Code:` lines, so the core appears in its own lineage; the architecture blueprint's order marks the step done.

### R_team: Team-work quality

**Acceptance Criterion:** Every lane routed through the home coordinator, the Z.AI seat engaged from the design on, verdicts recorded with their commit; friction logged as it happens.

### R_docs: Documentation

**Acceptance Criterion:** Changes reflected in ontology, implementation blueprints and module docstrings; the method's findings met here routed to its owners, not written into its zone from here.

### R_issues: Issues

**Acceptance Criterion:** Every problem met is fixed or logged.
