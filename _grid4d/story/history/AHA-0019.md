# AHA-0019: implement the safe credential surface: the git credential-helper protocol over the store, and the safe tutorial

## Goal

The call-model for the GitHub token (Human decision 2026-10-31, executed by EVOLUCEAN-0528) needs one missing surface on the ahabase side: git does not read a token from an environment variable, so routing git operations through the safe requires the git credential-helper protocol. This story adds `ahabase safe credential` - git asks, the safe answers from its store - and the safe tutorial, the capability's own documentation at the capability's home. It is the ahabase-side prerequisite of EVOLUCEAN-0528's R3, and the first place the incubator call-direction lands on real code.

## Requirements

### R1: `safe credential` speaks the git credential-helper protocol

`ahabase safe credential` implements the protocol git defines for credential helpers: git invokes it with a verb (`get`, `store`, `erase`) and a key/value request on stdin; a `get` for a host the safe holds answers `username`/`password` on stdout from the store's value; `store` and `erase` never write into the store (values enter only through `safe set` by the owner - the helper is a read surface, and a `store` call fails soft with a notice naming the owner's path). The host scoping comes from the manifest (the value's target/binding names the host, as `github-push-pat` already declares `git-credential github.com/<account-id>`); a request for an unknown host answers nothing (empty output, exit 0 - git's contract). The value crosses only the helper's stdout pipe to git: never a log line, never an error message, never a file.

**Acceptance Criterion:** `git credential fill` with the helper configured answers username/password from a fixture store; `store`/`erase` leave the store untouched; an unknown-host request yields git's contract behavior; a no-leak assertion proves the value appears nowhere outside the protocol pipe.

### R2: usable as the global helper for github.com

The surface is designed and measured for the global wiring EVOLUCEAN-0528 R3 performs: `credential.https://github.com.helper` pointing at `ahabase safe credential`, with osxkeychain remaining the helper for other hosts. Measured live: a real authenticated operation (fetch or push against a private repository of the ahabase org) through the helper route, with the keychain entry for github.com temporarily unreachable so the run proves the safe is the answering authority, not a fallback.

**Acceptance Criterion:** a live authenticated git operation succeeds with the helper as the only github.com credential source; the measured run is recorded with its command and result; the wiring instructions EVOLUCEAN-0528 follows are written (one config line, no per-command hacks).

### R3: the safe tutorial at the capability's home

A quality tutorial for the safe capability, in the ahabase package documentation (its Users-zone channel), covering the owner's walkthrough - `set`, `bind`, `run`, the credential helper, `refresh` of targets, rotation, `get --reveal` (the owner's interactive window - a Human condition of 2026-10-31), `compare` - and the user's walkthrough (how a tool receives a value as a bound consumer, what fail-closed looks like and its remedy). English, generic examples only: this is Public-perimeter content, so no real token, account, or employer appears.

**Acceptance Criterion:** the tutorial exists in the package docs, both walkthroughs present, every command it names is real (measured: each example command runs or is a documented failure mode), and the public-perimeter constraint holds (a name grep over the tutorial comes back clean).

### R2: live run, reset semantics, and the wiring instructions

Measured live from this worktree (branch `feature/AHA-0019-implement-the-safe-credential`, private origin):

```
GIT_CONFIG_SYSTEM=/dev/null GIT_CONFIG_GLOBAL=/dev/null GIT_TRACE=1 \
git -c "credential.helper=" \
    -c "credential.https://github.com.helper=!$PWD/.venv/bin/python -m ahabase safe credential" \
push --dry-run origin feature/AHA-0019-implement-the-safe-credential
```

Result: the trace names only the safe's helper (`credential get`, then `credential store` with the fail-soft notice on the successful-authentication report); send-pack completed - an authenticated operation against the private repository with the safe as the only github.com credential source.

Two measured facts about the environment that shape the wiring:

- Apple's git reads the system gitconfig (osxkeychain) even under `GIT_CONFIG_SYSTEM=/dev/null` - `git config --show-origin --list` still lists it under the nulling. The command-line reset `-c "credential.helper="` is what actually clears inherited helpers (a `credential-store` broadcast under the reset shows no osxkeychain invocation), and command-line entries evaluate after every file entry, so the reset clears them all.
- The helper stack on this machine besides any new wiring: system osxkeychain, global osxkeychain, and a repo-local `!gh auth git-credential` in the ahabase repository's config.

The wiring instructions EVOLUCEAN-0528 R3 follows (the tutorial's step 4, measured in rehearsal):

```
git config --global credential.https://github.com.helper ""
git config --global --add credential.https://github.com.helper "!ahabase safe credential"
```

with an installed `ahabase` on PATH (a package upgrade must land before this becomes the permanent wiring). The second line must be `--add`: a plain set would replace the empty entry, and the reset would be lost - measured both ways with a seeded stale keychain copy for a fixture host. With the reset (GIT_TRACE): osxkeychain is not invoked at all for the host, whether the safe answers or stays silent, and it keeps serving other hosts. Without the reset: osxkeychain stays in the list, runs before the url-scoped helper, and is consulted whenever the safe is silent - a stale keychain copy would answer. The repos in play are private: both `github.com/ahabase/evolucean` and `github.com/ahabase/ahabase` answer 401 to the anonymous `info/refs` probe - a visibility probe must be curl, not git, because `git ls-remote` on this machine authenticates silently through the keychain item the safe's git-credential target maintains.
