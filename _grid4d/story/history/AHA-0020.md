# AHA-0020: split the git-credential target's helper scope from its custody copy

> Story document defining work scope, requirements, and acceptance criteria.

**Type:** default
**Epic:** [AHABASE](AHABASE)
**Status:** completed
**Blueprint:** [implementation-story-blueprint](implementation-story-blueprint)

## Goal

A `git-credential` target on a safe entry carries two roles in one declaration: the host scope `ahabase safe credential` answers for (AHA-0019 reads it from the manifest), and the custody copy `safe set`/`safe refresh` maintain in the keychain through `git credential approve`. The first caller of the helper at scale (EVOLUCEAN-0528, the pure call-model for github.com) measured the coupling live: removing the target to retire the copy also silences the helper, because the declaration is the only thing that grants the scope. This story splits the two: a target variant that declares helper scope and maintains no copy - the honest form of "the safe answers for this host, and nothing else holds the value for it".

## Requirements

### R1: the scope-only variant, end to end

`ahabase safe target add NAME git-credential HOST ACCOUNT --no-copy` declares the host scope without a tool copy: the manifest entry carries `"copy": false`; `safe set` and `safe refresh` write nothing for it (and say so - the rotation report names it as scope-only, not as refreshed); `safe credential get` answers for a host whose only declaration is scope-only (the helper reads the store value - the load-bearing property EVOLUCEAN-0528 waits on); `safe list` shows the variant distinguishably from a copying target; the health check raises no finding for it (there is no copy to be missing); `safe target remove` matches it (the copy field never blocks removal); `--no-copy` on a `gh-login` target is refused (a gh login is a copy by definition - it has no scope role).

**Acceptance Criterion:** on a fixture manifest the full variant behaves as specified (add, rotation writes nothing, helper answers, list distinguishes, health silent, remove matches, gh-login refusal) - each property measured by a test, not asserted by prose; the default (no flag) is byte-identical to today's behavior.

### R2: the variant is documented at the capability's home

The safe tutorial (`docs/safe.md`) teaches the variant where targets are taught (step 5): what it is for (the pure call-model), the one-flag form, and that rotation then touches no tool store for it. The safe implementation blueprint records the field and its semantics (structure, rotation behavior, health behavior). English, generic examples only (public-perimeter content).

**Acceptance Criterion:** both documents carry the variant with a runnable example (the command and its measured output), and the public-perimeter grep over the tutorial stays clean.

## Notes

Created: 2026-10-31, on the Human's choice among the remedies for the coupling EVOLUCEAN-0528 measured during its R3 execution (the option list: an ahabase decoupling story first, or accept the coupling and keep the target as a declared fallback). The coupling, its measured evidence (helper silent without the declaration; helper green from the store with the keychain copy absent) and the interim machine state live in EVOLUCEAN-0528's story Notes and in its issue `safe-git-helper-target-couples-scope-and-custody` - both named in plain text here: this repository's link gate resolves links within itself only.

Measured state at mint (the ahabase main tree at merge-base 9df0610 with origin/main, past the release v0.0019.0.0000.00 tag):

- `GitCredentialTarget` (src/ahabase/safe.py): `parse` builds `{kind, host, account}`; `refresh` runs `git credential approve`; `Safe.credential` matches on kind+host+account and is already indifferent to extra fields - a scope-only declaration will answer with no code change there (R1 proves it by test).
- `_refresh_targets` refreshes and verifies every declared target; `Safe.health` checks every target's presence - both need the scope-only skip (a scope-only target is neither written nor missed).
- `Safe.target_remove` compares specs by dict equality - a `copy` field on the stored side would block removal (R1 normalizes the comparison).
- The CLI (`cli_safe.py`) parses `KIND SPEC` and prints the rotation report from the `refreshed`/`failed` lists.

Design decisions (recorded for the reviewer):

- The field lives on the target spec (`"copy": false`), not on a new target kind: one kind, two custody modes - the helper's matching stays unchanged.
- The default is copy-on: every existing manifest is valid as-is; the variant is opt-in per target.
- The rotation report says `scope target <label> - no copy is maintained` (a third outcome, not a fake "refreshed"): the label never lies about writing.
- `gh-login` refuses the flag: its only role is a copy; there is nothing to declare scope for.

Scope fences: this story adds the variant and its docs; it does NOT convert any real manifest entry (EVOLUCEAN-0528 R3 performs its own conversion after this lands), and it does not change the helper protocol surface itself (verbs, fail-soft semantics - AHA-0019's contract is frozen).

Review remedy (the CHANGES finding above; landed after 9432c27):

- `target_add` returns the replaced spec and keys its duplicate check on `_same_target` (equality on every field but `copy`, the same normalization `target_remove` uses): adding the spec of an already-declared target in the other custody mode converts the stored one instead of adding a second - the modes never coexist, so one rotation can never name the same target as both refreshed and scope-only. Conversion chosen over refusal on the `bind` precedent (a rebind replaces the same-path binding): one owner-gated step instead of a remove/add pair. The CLI says `converted to scope only` and names the leftover copy honestly (a copy already written in the tool's store, if any, stays until removed by hand); converting back says `converted to a maintained copy`.
