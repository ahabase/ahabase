# AHA-0014: safe on Windows - lock, platform dispatch, exec, prompts, permissions and CI parity

> The safe module is ahabase's first public capability and today it cannot even import on Windows - this story makes it one codebase that runs on macOS and Windows (and CI on Linux), the way ahabase is built.

**Type:** default
**Epic:** [AHABASE](AHABASE)
**Status:** completed
**Blueprint:** implementation-story-blueprint

## Goal

ahabase is built for macOS and Windows immediately (the colleagues run both; the owner tests on both - Human direction, 2026-10-30). The safe module is the first code capability, and it is POSIX-bound in five places: `import fcntl` at module top means the module fails at import on Windows (measured in the code, line 27); the manifest lock is `fcntl.flock`; `GIT_ASKPASS="true"` names a Unix executable that does not exist on Windows; executable and not-bindable detection is `os.access(..., os.X_OK)`, which on Windows answers yes to almost anything (PATHEXT decides); and the manifest's `0o600` has no direct meaning on NTFS. This story removes those five bindings with an established library and a small platform dispatch, proves both OS variants in CI on every story, and writes the rule down: every code-impacting story ships both OS variants in the same story.

## Requirements

### R1: The module imports and locks on every OS

**Acceptance Criterion:** no platform-only import sits at module top - the lock goes through the `filelock` library (an established wheel, not a hand-rolled lock), platform specifics live in `_win.py`/`_posix.py` siblings chosen at import time, and the lock's contract is unchanged (exclusive, released on process death, one writer at a time - the concurrent-sets test stays green unchanged).

### R2: Executable and not-bindable detection answers per OS

**Acceptance Criterion:** the exec check used by `bind`, by `run` (through the binding guard) and by `doctor` (the health check) resolves executables the way its OS does - `X_OK` on POSIX, `PATHEXT` suffixes on Windows - and the NOT_BINDABLE set covers Windows script suffixes (`.exe`, `.bat`, `.cmd`); a Windows-only binding target is refused with the same message shape as the POSIX one. (`compare` resolves no executable - it reads the current value; the measured check sites are `bind`, the guard `run` goes through, and the health check `doctor` runs.)

### R3: Prompts stay disabled and permissions stay owner-only on both OSes

**Acceptance Criterion:** the quiet environment disables prompts without naming a Unix-only executable on Windows (git's terminal prompt off, GCM non-interactive/GUI-off everywhere; the askpass no-op comes from the platform module); the manifest and lock file keep `0o600` on POSIX, and the Windows arm states what owner-only means there (the user profile directory's ACLs, inherited by the manifest) in code comment and blueprint.

### R4: CI proves both OS variants on every story

**Acceptance Criterion:** the suite runs in GitHub Actions on a matrix of macOS, Windows and Ubuntu; fixtures that need an OS-side script ship both variants (`.sh` and `.bat`) or use OS-neutral Python fixtures; the workflow file lands in this story and runs green on all three lanes.

### R_team: Team-work quality practiced and logged

**Acceptance Criterion:** a review seat measures the pinned commit and its verdict, naming the commit, is logged below.

### R_docs: Documentation complete

**Acceptance Criterion:** the layering path is a base concept, not story-local knowledge - [ontology-portability-blueprint](ontology-portability-blueprint) defines it (library → dispatch → own code, both variants per story) and the ontology index lists it (Human direction, 2026-10-30: document the multi-OS architecture in ontology and implementation, so the same mistake is not repeated); the delta blueprint `implementation-ahabase-safe-windows-blueprint` implements the concept and states the dispatch, the library choice and both-OS verification; the safe blueprint and integration blueprint name their Windows arms where the text claims OS behavior; the both-variants-per-story rule lands in AHABASE.md; decisions are recorded below.

## Decisions

- **filelock, not a hand-rolled lock (the standing rule):** the manifest lock's platform reach is a solved problem - `filelock` ships POSIX flock and Windows msvcrt locking behind one API; writing our own is the wheel we do not reinvent.
- **Import-time dispatch (`_win.py`/`_posix.py`):** the platform module is chosen once at import; `safe.py` stays one codebase with no `if platform.system()` scattered through it - platform differences have one home each.
- **CI matrix as the both-variants rule's enforcement:** a story that breaks the other OS turns the matrix red in its own story - the rule is measured, not remembered.
- **Layering for OS variants (library → dispatch → own code):** prefer a library that already solved it (filelock, shutil.which - the stdlib's own per-OS resolution); where behavior genuinely differs, the dispatch module owns it; only truly new behavior is ours.
- **The layering path is a base concept (Human direction, 2026-10-30):** the robust minimal path proven before us - [ontology-portability-blueprint](ontology-portability-blueprint) - so every future capability meets it as ontology, not as a discovered mistake.
