# AHA-0032: parallel story lifecycle under one lock

> N concurrent sessions mint, work, and complete stories in one Epic: the shared-tree phases of the ahabase package's story lifecycle run under one exclusive inter-process lock, work inside worktrees stays lock-free.

**Type:** default
**Epic:** [AHABASE](AHABASE)
**Status:** completed
**Blueprint:** implementation-story-blueprint

## Goal

Parallel work becomes a designed capability of the ahabase package's story lifecycle (the consumer CLI). Today only the work phase is parallel: concurrent create wedges the repository until manual git surgery, concurrent complete fails loud leaving a half-done state that a serial re-run heals, and create racing complete passes only by structural luck (measured 2026-11-21 - the issue filed with this story carries both races). The fix is one exclusive inter-process lock over every mutation of the shared tree, built on the lock primitive the package already ships, plus cleanup that holds for every death of the mint: a failure (any class, interrupts included) rolls back before refusing, and a kill that runs no rollback leaves a corpse the next create heals - never orphans, never a traceback, never manual surgery.

## Requirements

### R1: concurrent create is serialized - no wedge, no raw errors

The whole create critical section - the number scan, the ignore write, worktree add, the story-set commit - runs under one exclusive inter-process lock keyed on the repository's COMMON git directory: invisible to status, never in history, and ONE mutex per repository whichever tree the command runs from (the main root or the inside of a linked worktree - the normal seat of a parallel session). Two concurrent create processes both succeed with distinct numbers; the measured failure cascade (three collision layers: the shared index lock, the per-worktree admin lock, the filesystem interleaving) becomes unreachable.

**Acceptance Criterion:** A harness fires two create processes simultaneously per round, five rounds, in a scratch epic: every round ends with both stories minted, distinct numbers, no orphan branches, no prunable worktree-admin entry, one ignore line, and no traceback in any output. A create invoked from inside a linked story worktree takes the same lock file: an external holder of the common lock blocks it, and after both invocations the repository holds exactly one lock file.

### R2: concurrent complete is serialized - both land

Complete's main-tree phase - mark, tag, merge, archive window, worktree and branch removal - runs under the same lock. Two concurrent complete calls both land: each produces exactly one merge commit, tags stay distinct, the archive window holds.

**Acceptance Criterion:** The harness fires two complete processes simultaneously on two stories with committed sets: both report completed; main holds exactly one merge commit per story; both tags exist; no story worktree or story branch remains; a follow-up status counts both stories completed.

### R3: create racing complete - the benign window closes

A create fired while a complete holds the critical section waits for the lock (bounded) instead of refusing on the transiently dirty main tree, then mints the next number.

**Acceptance Criterion:** The harness fires complete and create at the same instant: both succeed, the create's number is exactly one past the completing story's, and no refusal names uncommitted changes.

### R4: crash and failure safety (red arms)

The lock releases on process death: a holder killed mid-critical-section wedges nothing - the next lifecycle command proceeds without manual pruning. The mint leaves nothing behind whichever way it dies: a failure inside create (any class - an OSError, an interrupt) rolls the worktree and branch back and refuses by name; a create killed outright (SIGKILL - no rollback can run) leaves a half-minted corpse (a story-named worktree whose branch holds no commit beyond the main branch, with or without the template writes landed), and the NEXT create heals every corpse inside the lock - worktree and branch removed, the number returned to the scan, no manual prune. The heal is strict: a corpse is exactly a killed mint's shape (the branch reflog holds only its creation entry, the dirt is limited to the mint's own template files) - anything else, notably a hand-merged story's worktree (the consumer landed it by plain git, so no commit sits beyond main either), survives a following create untouched, uncommitted files included. A worktree hand-made on a creation-only branch whose only dirt IS the mint's own template files is indistinguishable from a killed mint by design, and heals the same way.

**Acceptance Criterion:** (a) An external lock holder killed with SIGKILL: the waiting create proceeds with no manual prune; a half-minted corpse - both kinds, the bare one (branch at the main head, no writes) and the written one (the story document on disk, uncommitted, which the scan would otherwise skip past) - is healed by the next create: no corpse directory, no corpse branch, the number reused, no prunable admin entry; and a hand-merged story's worktree with an uncommitted file SURVIVES the next create: the worktree, the file and the branch stay, the create mints past - each strict leg witnessed ALONE: a hand-merged story with a CLEAN worktree survives (only the reflog leg protects it), and a hand-made worktree on a creation-only branch carrying one foreign file survives (only the dirt leg protects it), so deleting either guard alone turns the row red. (b) A failure injected between worktree add and the story-set commit - an OSError, click's Abort (SIGINT through the door), a raw KeyboardInterrupt - leaves no worktree directory and no branch: the refusal names the failure and the removal (an interrupt keeps its class at the engine; the door renders it exit 1), and the next create recovers.

### R5: parallel work stays lock-free

Work inside distinct worktrees never takes the lifecycle lock; the lock covers only shared-tree mutations.

**Acceptance Criterion:** While an external process holds the lifecycle lock, a plain git commit in a story worktree succeeds immediately; the lock file lives only inside the git directory and never appears in status or in any commit.

## Acceptance

- [x] R1 five rounds of paired concurrent creates: both minted, distinct numbers, no wedge; one mutex per repository whichever tree the command runs from
- [x] R2 paired concurrent completes: both land, one merge each, tags distinct
- [x] R3 create waits out a completing session, then mints the next number
- [x] R4 kill of a holder releases the lock; the next create heals a half-minted corpse (strictly - a hand-merged story's worktree survives untouched, each strict leg witnessed alone); every failure class (OSError, Abort, KeyboardInterrupt) cleans up and refuses by name
- [x] R5 work in worktrees never blocks on the lifecycle lock
