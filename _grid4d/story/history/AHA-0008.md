## Starting evidence for the transparency lane

Read by the work seat on 2026-10-26 from the method's tooling, described here by its surface only (what it does and what it misses, not where in its code - the detail went to the method's owners):

- **Lineage model:** concept blueprint -> implementation blueprint (`**Implements:**`) -> code (`**Code:**` module list; a module docstring `Implements:` back-link; a naming convention between blueprint and module); gaps reported as concept without root anchor, concept without implementation, implementation without code, implementation without concept - a reflexion model (convergence, absence, divergence).
- **Projections** are generated by `knowledge-usage sync` for every Epic found in the workspace, already including ahabase; they are declared per scope in a `*-projections-pattern.md`; mermaid is already used (fishbone diagrams).
- **For ahabase they come out empty or wrong today:** the identity has no `**CodeArtifacts:**` line (so orphans, gradients, artifacts and capability projections are skipped); the orphans scan expects the method's own blueprint layout; the lineage page runs at SubEpic scope only and reads the method's own source; several projections assume the method's own package path; one projection writes a fixed method-prefixed file name into every Epic.
- **First gap in ahabase itself:** only the safe blueprint carries a `**Code:**` line; the architecture blueprint (plugins, CLI) has none; no module carries an `Implements:` docstring.

The lane's question: generalize what evolucean has (it belongs to the base - structure that software can verify), or build it in the package from the start - and in which order, given the rule one place per capability and roadmap step 9 (the knowledge format moves into the package).
