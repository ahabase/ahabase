# AHA-0012: safe targets and rotation in one place

> One record per secret, every further copy a target the safe maintains, rotation one command - the ruled architecture, drawn and then built.

**Type:** default
**Epic:** [AHABASE](AHABASE)
**Status:** completed
**Blueprint:** implementation-story-blueprint

## Goal

The Human ruled (2026-10-30, shaped in the session of that day): the safe is the central place for the safe management of all secrets; rotation is done only there; every integration (git, dbt, the evolucean CLI) goes through the safe by one of three routes - in-process `safe://` resolution, `safe run` env transport, or a native-store target the safe maintains. That day's measured migration proved the shape by hand: three GitHub tokens of one account became one PAT - a keychain credential item for git and a gh login, both rewritten by hand during the switch. This story makes the ruled architecture explicit (ruling + diagram) and builds what the hand-work showed missing: targets in the manifest and rotation that refreshes them, so `safe set` is the whole rotation.

## Requirements

### R1: The ruled architecture, drawn and stated

**Acceptance Criterion:** the safe blueprint carries the ruling (rule 7 amended, the git row naming the helper item a target) and an architecture diagram (mermaid) showing owner/set, entry, store, targets, the three transports and the "a value nowhere else" invariant; every element of the diagram names the rule it is (transparent, robust, consistent, maintainable, minimal - Human, 2026-10-30).

### R2: Targets in the manifest

**Acceptance Criterion:** a manifest entry may name targets (kind and destination: a git credential helper's keychain item, a CLI login such as gh); `safe list` prints them; a malformed target is refused the way a malformed binding is; the manifest holds no value.

### R3: Rotation in one place

**Acceptance Criterion:** `safe set` of an existing name refreshes every reachable target in-process (git-credential: writes the helper's keychain item; gh-login: feeds the CLI on stdin) - the value is never printed and never appears in an argument list; a target that could not be refreshed is named in the output, and the command's result states it.

### R4: Health knows targets

**Acceptance Criterion:** `ahabase doctor` reports per target whether it is present (the keychain item exists; the CLI is logged in) - presence only, never a value.

### R5: Tests

**Acceptance Criterion:** the suite covers targets under the existing isolation (temporary `HOME`, the guard keyring, no real store): a refresh writes the target, a failing target is reported and not swallowed, a malformed target is refused; all rows green.

## Decisions

- **The ruling (Human, 2026-10-30):** the safe is the one place a secret is managed - one entry per secret; every place a value lives is either the safe's store or a target the safe writes and refreshes; rotation happens only in the safe; environment variables are transport, never storage.
- **Grounding fixture:** the same day's consolidation (three tokens of one GitHub account measured, one PAT left; the keychain credential item and the gh login rewritten by hand) - this story automates exactly that hand-work; the instance is the first dogfooding case ([safe-first-public-capability](safe-first-public-capability), conditions).
- **Naming:** a **target** (a copy in a tool's own store, maintained by the safe) is a different concept from a **consumer** (a bound executable receiving the value through `run`); the word "projection" is not used for it (taken by the knowledge projections).
- **AHA-0011 overlap - resolved:** AHA-0011 (work instance, same day) was a vision/docs story - the incubator model, sharing multiplies, the "Safe first" scope ruling (credentials including tokens for now, widening later); it touched no code and not the safe blueprint (measured at merge `8b35f14`, tag `v0.0011.0.0000.00`). No overlap with this story's targets and rotation; the two rulings of that day state one shape.
- **The agent boundary stands owed:** the safe blueprint's later step 5 places the agent guard before a wide-reach token moves into the OS store; the 2026-10-30 consolidation happened by the Human's direct decision that day and is recorded as such, not as a precedent.
- **A write is proven by presence (review finding, 2026-10-30):** `git credential approve` with no helper configured accepts the value and writes nothing, exit 0 - so `set` and `refresh` verify each target with `present()` after writing it; a destination that took nothing is a failure carrying the kind's own remedy message (`absence`), never a "refreshed" line. The kinds own their absence messages, so the remedy reaches the reported condition.
