## Goal

The first NEW capability of ahabase from the Human's priorities list after the safe (AHABASE-Priorities row 2): the llm connection core lands in this package as its own capability subepic, so that every ahabase user gets a model door beside the safe's secrets door. After this story ahabase can resolve an access path to a model (including the connection ladder and the session pin that is the path's per-session form), verify it with a classified failure, switch the tool's settings with backup and restore, and discover which paths a machine can use, none of which ahabase could do before. These are the four moving families of the base-versus-method cut; model selection, the model catalogue, the pattern-driven hook guidance, the proxy and service tooling, LM Studio management and telemetry stay with the method.

This is graduation 2 of the incubation pipeline and the landing half of a pair. The order inside the story is fixed by the Human (2026-11-08): the ontology first, then the implementation blueprint (which freezes the seam contract), then the implementation. The flip story on the method side is minted when the contract is frozen at the end of R2 and quotes it unchanged.

Constraints this story answers to (Epic and incubation rules): One place per capability; Links point inward (this story's documents name no document of the closed zone; the part of the method's dossier this story needs is extracted into its own documents); Safe first (the code touches the network and credentials: values arrive through the safe, never through a document); both OS variants in the same story; Knowledge written as public (no hosts, accounts or local paths); data stays with the instance (the per-machine variants file and the telemetry stay with the instance).

## Requirements

### R1: Ontology first - the ahabase-llm subepic

Found the capability subepic `ahabase-llm` (identity `AHABASE-LLM`, StoryPrefix `AHA-LLM-`, inherits ahabase, as the safe's is) with its ontology index and the minimal concept set the four moving families need: the access path (with its identity, the ladder it belongs to and its per-session pin), the verification with its failure classification, the settings switch with its backup and restore, and the discovery registry. Four concepts: the session pin is the access path in force for a session, not a separate concept. A concept enters only when it is robust, minimal and needed by the agreed implementation. The Epic ontology changes only by the capabilities-index entry and, if the architecture needs it, one relation to the Door concept; no capability concept is added at Epic level.

**Acceptance Criterion:** the subepic identity, the ontology index and one blueprint per concept exist in `_grid4d/subepic/ahabase-llm/`; a table in the index maps every concept to the code family that needs it (a concept with no family is removed; this clause and "robust, minimal, needed" are reviewer readings against the table, not a command); the Epic ontology diff is limited to the capabilities index entry (and the Door relation if justified); no document names a closed-zone document; the by-name link census of the Epic reports zero unresolved.

### R2: Implementation blueprint - the seam contract frozen

`implementation-ahabase-llm-blueprint` names the modules that land (the four families of the base-versus-method cut), the module layout in the package, the import of the config door that now stays inside the package, the platform dispatch for the OS-specific parts, a FUNCTION-LEVEL CUT table (every public function of `path_resolution`, `path_verification`, `discovery` and `paths` marked moves or stays, with the reason; `path_verification` mixes the moving verify, switch, restore, session-payload and classification functions with the staying service recovery and proxy validation), the CREDENTIAL FLOW required by Safe first (below), and the SEAM CONTRACT: type (library seam for the method plus a door `ahabase llm ...` behind the one registry), the surface as named functions per module, the floor (a released tag) and the custody boundary (implementations move; per-instance data, model selection and catalogue, hook guidance, provider tooling, proxy and service management, LM Studio management, telemetry and collaboration wiring stay with the method). The contract is written once and frozen at the end of this requirement.

**Credential flow (Safe first):** the ported code must not make the open package a place where credentials sit in the clear. The blueprint states, for every credential the moving code touches, how it arrives (a path's auth is a reference: an environment variable injected by the safe into the consumer process, or a key helper command that asks the safe) and what is written to disk. The session payload that today carries the resolved token in a 0600 file is replaced by a payload that carries a key-helper reference, or the blueprint records why a literal at rest is unavoidable and what bounds it; no credential value is printed or logged.

**Acceptance Criterion:** the blueprint carries a section "Seam contract (frozen)" whose text is copied byte-for-byte into the flip story at its minting (measured by diff, empty); every surface function named in it exists in the code after R3 (checked by a test that imports each by name); the blueprint links the ontology concepts of R1 and the ontology links back; no document of the blueprint names a closed-zone document (the same check as R1). Completion order: R2 freezes, R6 mints the flip story, then the diff clause above and R5's "the flip story names it" are checked.

### R3: Implementation - the port, one family at a time

Port exactly what the R2 function-level cut marks as moving, in three reviewable families, one commit per family, each with its own tests, planted mutants, scans and reviewer checkpoint. The config-door imports are repointed inside the package; nothing imports a method package; the platform dispatch covers what differs between macOS and Windows; credentials follow the R2 credential flow.

- **R3a Access path and discovery:** `path_resolution` (definitions, auth, current-path identity, rescue order) and `discovery` (introspection, local availability, the registry), with the ladder schema.
- **R3b Verification and failure classification:** the preflight request, the verification family check, `classify_failure` with its hints, and the cheap reachability sensors that belong to the moving cut.
- **R3c Settings switch, restore and session payload:** the verified switch, the atomic settings write with backup, the restore, and the session payload with the key-helper reference of the credential flow.

**Acceptance Criterion (each family):** its tests pass with the planted mutants shown red then reverted; a canary test proves that no credential value reaches stdout, a log line or a file other than the one the credential flow names; a static check asserts that nothing in the package imports a method; the containment and trust-zone scans over everything that family moves are clean (exact commands recorded in the Notes); the Windows leg is covered by the CI matrix definition and its result is read from the CI run, not claimed.
