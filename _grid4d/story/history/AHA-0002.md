# AHA-0002: Secrets mechanism: ahabase secret interface with pluggable backends (OS store default), references instead of values, process-scoped resolution - nothing switched on the instance

> The mechanism every door and plugin will use for secrets, built and tested on fictional secrets only; no secret of the instance is moved or read.

**Type:** default
**Epic:** [AHABASE](AHABASE)
**Status:** completed
**Blueprint:** [implementation-story-blueprint](implementation-story-blueprint)

## Goal

Secrets (tokens, API keys, passwords) of an ahabase instance live today in git remote URLs, shell profiles and configuration files, where tools and LLM sessions can read them. The secrets service of the open package gives one interface with pluggable stores, references instead of values in configuration, and resolution only into the process that needs a value.

Human decision 2026-10-24: changing how the instance's secrets are stored or used is an extremely risky step, taken only with proven end-to-end function, a known impact on every consumer and a tested rotation; tokens staying a while longer where they are is acceptable. This story therefore builds the mechanism only: nothing on the instance is switched, moved or read. The inventory of consumers, the shadow run, the rotation procedure and the switch of each consumer are later steps, each with the Human's consent.

## Requirements

### R1: Secrets blueprint

`_grid4d/implementation/implementation-ahabase-safe-blueprint.md`: the reference syntax, the store interface, the stores of this story, the manifest (names and metadata, never values), resolution into a child process, output rules (no value is ever printed unless asked for explicitly), the zone (values are Intimate, the code is open), the known limits of the OS store, and the later steps (inventory, shadow run, rotation, switch one consumer at a time).

**Acceptance Criterion:** The blueprint exists with these sections and validates.

### R2: Store interface and stores

`ahabase.safe`: a store protocol (`get`, `set`, `delete`, `exists`) and three stores - `keyring` (the OS store through the `keyring` library: macOS Keychain, Secret Service, Windows Credential Manager), `env` (read-only, from environment variables, for CI) and `memory` (tests). The store is chosen per secret in the manifest, default `keyring`.

**Acceptance Criterion:** Each store passes the same contract tests; the `keyring` store is tested against a fake keyring backend, never the real OS store.

### R3: References and the manifest

A reference `safe://<name>` names a secret; the manifest (`<workspace>/_config/safe.json`, or `AHABASE_SAFE_MANIFEST`) holds per name: store, store key, purpose, owner, scope, created, expires, last rotated - never a value. `resolve(reference)` returns the value; a configuration value that is not a reference is passed through unchanged, so a consumer can switch to references one at a time.

**Acceptance Criterion:** Resolving a reference reads the store the manifest names; an unknown name is an error naming the secret but no value; a plain value passes through unchanged.

### R4: The `ahabase safe` commands

`set NAME` (value read hidden from the terminal or stdin, never from an argument), `list` (names and metadata), `run --env VAR=safe://NAME ... -- COMMAND` (values only in the child's environment), `get NAME` (refuses to print unless `--reveal`), `delete NAME`; `doctor` gains a health check: the default store is available, every manifest entry resolves (exists, no value shown), expiry within 14 days warns.

**Acceptance Criterion:** With the memory store: `set` from stdin, `list` shows no value, `run` gives the child the value while the parent's output carries none, `get` without `--reveal` refuses, `doctor` reports a missing and an expiring secret.

### R5: Nothing on the instance is touched

The tests use temporary manifests and the memory or fake stores only; no test or command of this story reads the instance's real secrets, remotes or shell profiles.

**Acceptance Criterion:** The suite runs with `HOME` and the manifest pointed at a temporary directory; a test fails if the real OS keyring backend is called.
