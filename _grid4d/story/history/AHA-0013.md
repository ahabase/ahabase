# AHA-0013: safe review findings: prove a refresh by the stored value, not by presence

> The delta review of AHA-0012 found the presence-proof too weak for a rotation's steady state - this story closes its findings before real targets are registered.

**Type:** default
**Epic:** [AHABASE](AHABASE)
**Status:** completed
**Blueprint:** implementation-story-blueprint

## Goal

AHA-0012 shipped rotation that refreshes a secret's targets and proves each write by presence. Its delta review at b3b0df7 (reviewer-deepseek seat, static-only - three APPROVE verdicts arrived first and the story was released on the first valid verdict, so these findings route forward) found the proof and the messages weaker than their claims: presence is satisfied by a stale copy from the previous rotation (the steady state of a rotation - nothing compared the value written with the value stored), and the git absence remedy points at a config that answers `osxkeychain` in the likeliest macOS failure (a helper configured, its item absent). This story proves a refresh by reading the destination back and comparing it with the value written, scopes the absence messages to what they can honestly name, and adopts the bare Run at line convention the freshness mechanism reads.

## Requirements

### R1: A refresh is proven by the stored value

**Acceptance Criterion:** after `refresh`, each kind reads the destination back (git: `git credential fill`; gh: `gh auth token`) and compares it with the value written - the digest, in constant time, in-process, never printed; a stale copy fails the proof with the kind's absence message; `present()` stays for health, which has no value at hand; every kind in the registry carries the proof members (`absence`, `verify`), asserted by a test.

### R2: The absence messages reach the conditions they fire on

**Acceptance Criterion:** the git absence message names both causes without claiming which fired (no helper configured, resolution following the directory the safe ran in; or a helper configured whose store holds no item - a locked keychain, an item never written); the gh message names a login existing with a different or stale token; the prompt test is armed against ambient `GCM_*`/`GIT_*` values (`monkeypatch.delenv` before the call).

### R3: Records and conventions

**Acceptance Criterion:** AHA-0012's record completes: the two late verdicts (deepseek-reviewer APPROVE; reviewer-deepseek REQUEST CHANGES with the issue links) are appended to its Review section, and its tests file carries exactly one bare Run at line with the counts in prose; the three issue files land; the safe blueprint's rule 7 sentence states what the mechanism now proves.

### R_team: Team-work quality practiced and logged

**Acceptance Criterion:** a review seat measures the pinned commit and its verdict, naming the commit, is logged below.

### R_docs: Documentation complete

**Acceptance Criterion:** the blueprint, the integration blueprint and the issue files state what the story built; decisions are recorded below.

## Decisions

- **Routing (Human, 2026-10-30):** the late REQUEST CHANGES findings ride this fix story; Windows parity moves to the next story - the fixes land before the owner registers real targets and relies on one-command rotation.
- **Verify, not presence (the reviewer's direction):** `present()` (health - no value at hand) and `verify(spec, value)` (refresh - the value just written) are separate protocol members; the comparison is sha256 digests with `hmac.compare_digest`, the read-back value lives only in the checking process and is never printed (rules 5 and 8 untouched).
- **gh read-back:** `gh auth token --hostname H` prints the token - captured, compared, dropped; the check runs on the scrubbed environment like every gh call.
